## 提议给前端的最小数据契约
以 v3.1 路由为基础，不在本稿宣称接口已经实现。
| 数据 | 必需字段 |
|---|---|
| 已领取签文 | reading_id、hexagram_id、名称、上下卦、lines_bottom_to_top、base_reading、content_origin、session_expires_at |
| 深解任务 | task_id、theme、status（pending/running/succeeded/failed）、成功内容或 error_code |
| 会话错误 | invalid_token / expired / claimed / session_expired；映射 UI 文案 |

模型返回 06 中的文字对象，B 添加上述业务元数据。服务端用会话检查 reading_id 归属；客户端不接受修改卦象。线上字段名最终由 A/B 共同锁定，不能只依据本提案直接改另一人的实现。

原 PRD“设备认证密钥只在后端”的措辞还需 B 细化：模型 Key 仅服务端；设备怎样持有或获得自身认证凭据需要明确，不由 A 擅自设计。

## Pitch 内容骨架 v0.1
1. 开场：“遇事不决，摇壳问问。” 描述小纠结、仪式与留存的产品设想。
2. 产品：一件可摇动的东方器物，通过上下卦灯光和真实纸签形成体验。
3. 演示：摇动 → 出签 → 屏幕码 → 主题深解 → 保存。素材分别标注真机实录或设计示意。
4. 用户：自用和赠礼两种场景是待验证假设；放真实访谈原话与样本数，不编购买意愿比例。
5. 商业：以实体销售为主；成本填真实 BOM，定价填测试方案，未测就标待验证。
6. 证据与后续：已完成的功能、失败记录与下一步；双龟/NFC/云收藏放未来，不混入本轮演示承诺。

比赛官方评审标准和提交格式尚未提供，以上不是主办方要求。需明确路演时长后再制作页数和逐页讲稿。
